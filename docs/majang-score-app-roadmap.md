# Mahjong Score App 開発ロードマップ

## 1. 目的

現在開発中の `majang-score-app`
を、まず実用できるWebアプリとして完成させ、その後ポートフォリオとしての技術的価値を高めながら、最終的にはAndroidアプリとしてGoogle
Playで公開することを目指す。

基本方針は以下。

-   最優先は「アプリを完成させ、実際の麻雀で使える状態にする」こと
-   学習目的で技術要素を増やすが、完成を妨げる過剰な技術導入は避ける
-   現在のGAS + Google Sheetsは暫定バックエンドとして活用する
-   将来的にSupabase / PostgreSQL等の一般的なバックエンド構成へ移行する
-   Web版完成後、PWA化・モバイルアプリ化へ段階的に進める
-   各段階で「なぜその設計にしたか」を説明できる状態にし、ポートフォリオとして残す

------------------------------------------------------------------------

## 2. 現状

主な技術構成：

-   React
-   TypeScript
-   Vite
-   IndexedDB / Dexie
-   Google OAuth
-   Google Apps Script
-   Google Sheets
-   GitHub Pages
-   GitHub Actions

現在は、端末内のIndexedDBをローカルデータストアとして利用し、GAS +
Google Sheetsを端末間共有用の簡易バックエンドとして利用している。

実装済みの主な土台：

- Room / Session / Hand のデータモデルとIndexedDB migration
- JSONバックアップ / 復元
- GASへの手動保存 / 取得
- Google OAuth、`revision` による保存競合の検知
- PWA Manifest、Service Worker、ホーム画面追加向け設定

未完了なのは、新規端末がJSONを受け渡さずにルームへ参加する導線、実機での継続運用によるUX・同期挙動の検証、最低限の自動テストとCIである。

概念的には以下。

``` text
React
  |
  v
IndexedDB
  |
  | 手動同期
  v
Google OAuth
  |
  v
Apps Script API
  |
  v
Google Apps Script
  |
  v
Google Sheets
```

同期時には `revision`
を利用し、他端末で更新された古いデータによる上書きを防止する。

現状、新しい端末にルームを共有する際にはJSONのエクスポート /
インポートが必要であり、ここが共有体験上の大きな改善ポイント。

# Phase 1: Web版・PWAの基本機能を実運用で完成させる

## ゴール

仲間内の実際の麻雀で、問題なく1回の対局を記録できる状態にする。

この段階では、新技術の導入よりも既存機能の完成度を優先する。

## 主な作業

-   点数記録
-   対局開始 / 終了
-   局履歴の確認
-   入力内容の修正 / 取消
-   対局履歴一覧
-   データバックアップ / 復元
-   スマートフォン表示の改善
-   エラー表示の改善
-   PWAの実機確認（ホーム画面追加、オフライン起動、更新時の挙動）
-   点数計算・集計ロジックをUIから分離し、テスト可能な純粋関数として整理する
-   画面コンポーネントを、既存機能の挙動を変えない範囲で段階的に分割する
-   実際の対局で使用してバグ・UX上の問題を洗い出す

## 完了条件

実際の麻雀で複数回使用し、通常の対局記録・PWA利用について大きな不満・致命的な不具合がないこと。

# Phase 2: 共有コードによるルーム参加を追加する

## ゴール

JSONファイルを受け渡さなくても、別端末から同じルームに参加できるようにする。

GASへの手動保存 / 取得、OAuth、`revision` による競合検知は実装済みである。このフェーズでは、それらを維持したまま初回参加の導線を追加する。

## 共有コード方式

ルーム作成時に共有コードを発行する。

例：

``` text
K7M4Q2
```

参加者は共有コードを入力するだけでルームを取得できる。

``` text
端末A
  |
  | ルーム作成
  v
GAS / Google Sheets
  |
  | shareCode = K7M4Q2
  v
共有コードを表示


端末B
  |
  | K7M4Q2 を入力
  v
GAS
  |
  | ルーム検索
  v
ルームデータ取得
  |
  v
IndexedDBへ保存
```

## データ例

``` text
roomId       shareCode   revision   payload
------------------------------------------------
UUID-xxxxx   K7M4Q2      5          {...}
```

共有コードは内部的な `roomId` とは分離する。

-   `roomId`: システム内部の一意な識別子
-   `shareCode`: ユーザーが入力・共有する短いコード

## 同期処理の設計方針

UIからGAS固有の処理を直接呼び出さない。

同期処理は可能な限りサービス層に閉じ込める。

イメージ：

``` text
UI
 |
 v
SyncService
 |
 v
GAS
```

想定する操作：

``` ts
createRoom()
joinRoom(shareCode)
pushRoom()
pullRoom()
```

既存の `pushRoom()` / `pullRoom()` は実装済みであり、`createRoom()` / `joinRoom(shareCode)` を共有API・UIへ追加する。

## アクセス方針

共有コードはルームを見つけて参加するための導線であり、それ自体を認証・認可の代替にしない。

- 初期版では、GAS API実行を許可したGoogleアカウントのみがアクセスできる構成を維持する
- 共有コードの推測・漏えい時に誰が閲覧・更新できるかを、実装前に明文化する
- 将来Supabaseへ移行する際は、`room_members` 等によるルーム単位の認可へ発展させる
- 参加者の削除や権限変更が必要になった時点で、共有コードのみの運用を拡張する

将来バックエンドを変更した際に、

``` text
GasSyncService
      ↓
SupabaseSyncService
```

のように置き換えやすい構造を意識する。

## 将来的な追加

共有URLにも対応する。

例：

``` text
https://example.com/?room=K7M4Q2
```

URLを開くだけでルーム参加画面へ遷移できるようにする。

JSONエクスポート /
インポート機能は削除せず、バックアップ・復旧用途として残す。

# Phase 3: 実運用を通じた共有・PWAの改善

## ゴール

Webアプリのコードを大きく変更せず、スマートフォン上で通常のアプリに近い使用感と、複数端末での安全な手動同期を実現する。

## 主な作業

-   スマートフォン向けUI改善
-   ホーム画面追加、オフライン起動、更新時の実機検証
-   同期の状態表示・エラー表示の改善
-   同時更新時に利用者が迷わない競合解決手順の検証
-   実対局で共有コード参加・手動同期を利用し、改善点を収集

## 目標構成

``` text
PWA
 |
 +--> IndexedDB
 |
 +--> SyncService
        |
        v
     GAS / Sheets
```

IndexedDBを利用しているため、通信できない状況でも対局記録自体は継続できる設計を維持する。

## この時点を最初の「完成」とする

Phase 3まで完成した段階で、一度アプリとして完成扱いとする。

仲間内で継続利用し、実利用から改善点を収集する。

# Phase 4: バックエンドをSupabaseへ移行

## ゴール

GAS / Google
Sheetsを暫定バックエンドから、本格的なDBを利用した構成へ移行する。

想定構成：

``` text
React / PWA
     |
     v
  Supabase
     |
     v
PostgreSQL
```

将来モバイルアプリを追加した場合：

``` text
Web / PWA ----+
              |
              v
           Supabase
              |
              v
         PostgreSQL
              ^
              |
Android ------+
```

## 学習対象

-   PostgreSQL
-   RDB設計
-   SQL
-   主キー / 外部キー
-   Migration
-   Authentication
-   Authorization
-   API
-   データ同期
-   競合制御

## DB設計

Google
Sheets上でルーム全体をJSONとして保存する方式から、必要に応じて正規化されたテーブル構成へ移行する。

例：

``` text
users
rooms
room_members
sessions
hands
```

具体的な正規化範囲については、現在のデータモデルと利用パターンを確認したうえで決定する。

## 認証

現在のGoogle OAuthは、Apps Script
APIを利用するための認証という側面が大きい。

バックエンド移行後は、

``` text
Google Login
     |
     v
ユーザー認証
     |
     v
アプリのデータアクセス
```

という、本来のユーザー認証として整理する。

Supabase Auth等の利用も検討する。

# 現時点での重要な設計方針

## 1. 完成を最優先する

新しい技術を使うこと自体を目的にしない。

「この技術を入れれば勉強になる」という理由だけで、現在必要のない技術を追加しない。

## 2. GASは捨てる前提ではなく、段階的移行のための暫定バックエンド

現在のGAS / Sheets実装を完成させる。

その経験を踏まえてSupabase /
PostgreSQLへ移行することで、バックエンド移行そのものも学習対象とする。

## 3. UIとバックエンド依存を分離する

UIがGASやSupabaseを直接意識しない構造を目指す。

``` text
UI
 |
 v
Application / Service
 |
 v
Sync / Repository
 |
 +--> GAS
 |
 +--> Supabase
```

将来のバックエンド変更を容易にする。

ただし、過度な抽象化は避け、現在必要な範囲で実装する。

## 4. IndexedDBを活かす

サーバーDBを導入しても、IndexedDBを単純に削除するとは限らない。

麻雀の対局中というユースケースを考え、

-   通信不良でも記録可能
-   入力レスポンスが速い
-   後からサーバー同期可能

というオフラインファースト構成を検討する。

## 5. 品質対策を移行後まで待たない

ポートフォリオとしてのテスト拡充・設計資料の整備は後段で進めるが、データを壊すリスクが高い領域は早い段階から検証する。

- 点数計算
- IndexedDB migration
- バックアップ復元
- 同期payloadの変換
- `revision` による競合判定

共有機能やDB移行の前に、これらの最低限のテストとbuild / lintのCIを整備する。

## 6. 実装理由を残す

Codexを利用して実装する場合でも、生成されたコードをそのまま採用するのではなく、

-   なぜこの設計なのか
-   他にどんな選択肢があるか
-   何をトレードオフしたか
-   データがどう流れるか
-   エラー時にどうなるか

を理解できる状態にする。

重要な設計判断については `docs/` またはREADMEに残す。

# 直近の次タスク

まずは **共有コードを利用したルーム参加機能** を実装する。

実装前に現在のコードを確認し、以下を整理する。

1.  現在のRoomデータモデル
2.  `roomId` の生成方法
3.  GASへ送信しているデータ形式
4.  Google Sheetsの現在のカラム構成
5.  `sync.ts` の責務
6.  GAS側の保存 / 取得処理
7.  revisionによる競合制御
8.  新規端末へルームを登録する現在の処理
9.  共有コードとGoogleアカウントアクセスの関係
10. 共有コードの漏えい・推測時の扱い

そのうえで、既存設計を壊さない最小変更で共有コード機能を追加する。共有コードは参加導線として扱い、認証・認可を単純なコード入力だけに依存させない。

この段階ではSupabase移行やReact Native化は行わない。

------------------------------------------------------------------------

## Codexへの実装方針

実装を開始する前に、まずリポジトリ全体と関連コードを確認し、現在の設計を説明すること。

その後、

1.  変更対象ファイル
2.  データモデルへの変更
3.  GAS / Sheetsへの変更
4.  フロントエンドへの変更
5.  既存データとの互換性
6.  エラーケース
7.  テスト方法

を含む実装Planを提示すること。

Planを確認してから実装へ進む。

既存機能を不必要にリファクタリングせず、共有コード機能に必要な最小限の変更を優先すること。
